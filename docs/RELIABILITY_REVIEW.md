# Follow-up reliability review and build order

Review triggered on 2026-10-07 by a real user report: adding more of a product did not increase the cart badge and the product card showed no ordered quantity. Work remains on the local branch. No deployment, real SMS, payment, or customer message was performed.

## What the report exposed

The badge used the number of distinct cart lines. The server could correctly hold two bags while the badge still displayed one product. Cards always displayed “Add to cart,” hiding that quantity. Earlier tests checked order totals and successful mutations but did not check this feedback after repeated adds. Filling an input in one operation also missed a separate failure when a person typed digits sequentially on a slow connection. A clean baseline now proves that typing `12` could leave `1`: the intermediate write disabled the input before the second digit.

The review traced the customer catalogue/cart, account/address, checkout, order/reorder and quotation flows, and owner navigation, dialogs, quotation terms and fulfillment. Backend checks covered ownership, idempotency, stock/payment transactions and concurrent address creation. It is a bounded review with explicit regression evidence, not proof that every possible defect is gone.

## Choices and tradeoffs

| Choice                         | Decision now                                                                                                                                                                | When to reconsider                                                                                                                                                                                 |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cart count                     | Count ordered selling units; show distinct materials in the accessible label and cart summary. Each card retains its unit, so a “unit” may mean a bag or a configured pack. | Add separate volume/weight totals only after defining valid conversions. Do not add unlike units together as weight.                                                                               |
| Cart responsiveness            | Show server-confirmed values and allow one cart write at a time per browser session. This avoids claiming stock/quantity changes before acceptance.                         | Add a queued or optimistic editor only if measured latency makes the simpler behavior unusable; it would need rollback and conflict handling.                                                      |
| Concurrent device cart editing | Server validates absolute quantities, ownership, stock and checkout reviews; refresh loads current state.                                                                   | If customers need simultaneous editing from several devices, add cart revisions/conflict UI or idempotent atomic increments. A browser-local guard cannot coordinate different devices.            |
| Reorder idempotency storage    | Reuse the existing durable audit table for a small per-user UUID receipt; serialize before checking it, including empty reorders.                                           | Use a dedicated operation table if several more workflows need large receipts, expiry or separate retention. Old clients without a key remain backward compatible; current UI always supplies one. |
| Existing stack                 | Keep NestJS/Prisma/PostgreSQL, Next.js and Expo/shared contracts.                                                                                                           | Rewrite only for a measured limitation that cannot be addressed locally. A rewrite would reset verification effort.                                                                                |
| Browser versus native launch   | Finish the responsive browser flow and test on the actual phones first.                                                                                                     | Ship native builds when device testing shows a requirement for native payment, reliable push or device integration. Browser screenshots/JS exports do not prove native behavior.                   |
| Cash versus online payments    | Start with COD and accurate collection/refund evidence. Online payments stay disabled.                                                                                      | Enable only after provider test-mode callback/webhook/reconciliation/refund and actual-device checks pass.                                                                                         |
| Pricing automation             | Manual selling-price entry and reviewed imports remain usable without AI.                                                                                                   | Add live OCR/AI after manual operation is dependable and costs/private storage are configured. AI output must still require human review.                                                          |
| Free hosting                   | Suitable for supervised staging with disposable, labelled test data.                                                                                                        | Production needs a service level compatible with order alerts, backups and expiry processing. Sleeping hosts/free database expiry are material limits.                                             |

## Recommended build sequence

1. **Finish the local reliability gate.** Re-test this cart report first, then the ₹20,000 COD smoke test in [LOCAL_TESTING.md](LOCAL_TESTING.md). Exercise a declined delivery, physical return and accepted quotation. Accept this phase only when quantities, cash and stock match the actual recorded events and the owner needs no developer guidance.
2. **Configure the real shop model.** Supply product photos, selling units/pack sizes, minimums/steps, prices, opening stock, named staff and genuine delivery pincodes/charges. Keep one shared inventory until separate retail/wholesale stock and settlements are explicitly agreed. Decide deposits, credit, partial supply/refunds and tax invoicing before implementing those policies.
3. **Run the family usability review on their phones.** Father and Uncle should each complete the Hindi script without coaching. Check real keyboard entry, large text, browser Back, calls/WhatsApp, intermittent mobile data and expired sessions. Prioritize anything that prevents them finishing daily work over adding features.
4. **Create separate staging after explicit authorization.** Follow [FAMILY_REVIEW.md](FAMILY_REVIEW.md): labelled test orders, correct cookie origins/proxy/SSE, staging-only secrets, migrations, private uploads, backups and a tested restore. Verify real SMS costs/recipient setup. Keep payments disabled.
5. **Harden the production release.** Run container/CI checks where Docker is available, review remaining dependency advisories, test backups/restore, access revocation, HTTPS/origins and error/uptime monitoring. Choose hosting that meets the shop's actual response-time needs. Deploy only when explicitly requested.
6. **Run a small supervised COD pilot.** Use a few known customers and a limited delivery area. Reconcile cash, cancellations, returns and stock daily. Record failed actions and support time. Confirm someone sees every new order while the app is in use; separately verify any promised closed-app alert mechanism.
7. **Add online payments and native capabilities one at a time.** Start in provider test mode, verify uncertain outcomes and refunds, then perform actual-device tests. Keep a named technical escalation path. Do not treat mocks or payment screenshots as proof.
8. **Expand business features only from observed demand.** Credit/deposits, partial deliveries, GST invoicing, multiple inventories, accounting exports and AI imports each need agreed rules and focused regression tests. Avoid adding them all before the COD pilot teaches which ones matter.
