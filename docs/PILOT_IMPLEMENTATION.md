# Pilot implementation plan

Keep Expo, Next.js, NestJS, Prisma/PostgreSQL and the existing transaction/payment boundaries. No new infrastructure or UI framework.

1. **Inventory:** extend existing product records with pack description, minimum quantity and quantity step. All quantities remain integer selling units (kg, bag, piece, box, etc.). Add an immutable movement ledger with opening-balance migration; product stock remains the transactionally maintained balance. Purchase, walk-in sale, damage, return and adjustments require a reason and idempotency key. Online reservations/cancellations write movements in the same transaction.
2. **Pagination:** bounded keyset pages with a unique ID tie-breaker, validated opaque cursors and filters; shared page response used by every caller. Add query indexes. Catalogue search, category/brand/availability and price/name/newest ordering run on the server. Reset pages after filter or SSE changes.
3. **Delivery:** exact six-digit pincodes belong to configurable zones, with charges, minimum, free threshold, estimate and active state. No production serviceability is inferred from “Bihar”. Checkout records zone/version and revalidates it before stock reservation. Seed only explicitly labelled development zones.
4. **Security:** staff OTP plus per-staff passphrase, short staff sessions, safe session/device metadata and revocation, persistent hashed-IP OTP budgets. Customer deletion anonymizes profile and clears nonessential personal data while retaining disclosed financial records. Contractor requests require audited staff verification. Quote decisions record source/reason. Uncertain gateway creation stays locked until independently verified reconciliation.
5. **Experience:** concrete #E7E6E1, warm sand #D9C9A8, graphite #252C2B, off-white #F7F6F1, construction amber #E9AD32 and safety green #386451. Native system sans for readable body, bold condensed-looking display treatment, monospace specification labels. A materials-counter layout puts live prices, selling units and delivery above promotional copy. Existing real product images take priority; missing photos are honestly labelled rather than invented brand photography. Store desk exposes stock movements, zones, account/session controls and audit history.
6. **Verification:** migrate existing data; test concurrent inventory, idempotency, zone changes, pagination boundaries, authorization, OTP limits, deletion and payment recovery. Run lint, typecheck, unit/integration/browser suites and all builds. Inspect narrow/mobile views, focus targets and error states.

Primary files: Prisma schema/new additive migration, shared contracts, API catalogue/orders/admin/quotes/payments/auth plus small inventory/pagination/security modules; customer store/catalogue/account/orders/quotes/checkout; store desk page/products/settings/quotes/styles; integration/browser tests. Preserve old migrations. Deploy API and clients together because list response contracts change. Back up before migrating; rollback application together, retaining additive tables and ledger data. Never roll stock history back by dropping its table.

Research (2 October 2026): [Infra.Market](https://infra.market/) groups materials by construction use and makes brands/support prominent; [Moglix](https://www.moglix.com/) emphasizes delivery location, brand/category browsing and detailed specifications. BuildersMART was inaccessible behind browser verification. The implementation uses these functional observations, not their layouts, promotional claims or imagery.

Verification results and remaining release prerequisites will be appended after implementation.

## Implemented outcome

The existing monorepo and database remain authoritative. An additive migration adds the stock ledger, product ordering rules, delivery zones, staff assurance, contractor verification, quote decision provenance, and pagination/search indexes. No runtime dependency or extra infrastructure was added. Legacy delivery amounts are retained for compatibility, but pincode-zone policy controls new checkout reviews.

Customer and admin screens now share graphite/concrete/sand/amber styling. Home exposes browse, prices, reorder, bulk quote, delivery lookup, and store contact actions. Product cards lead with unit/price/specification and show an honest placeholder until real photography is supplied. Search/categories remain visible; secondary filters expand when needed. Both apps have loading/error/retry/empty states, readable controls, and bounded list loading. Closed mobile admin navigation is hidden from keyboard/screen-reader traversal.

## Remaining gates before a 10–20 customer COD pilot

1. Deploy one always-on HTTPS API, managed PostgreSQL, and sibling-domain frontends. Apply the migration with `pg_trgm` permissions, release API/clients together, bootstrap per-staff passphrases, verify health alerts, and restore a backup into an isolated database. This rollout changes list response contracts; older native clients need an update/compatibility plan.
2. Configure and test real SMS OTP delivery in India. Production rejects mock OTP and credentialless staff. Keep online payments disabled for the COD pilot; Razorpay order/webhook/recovery/refund behavior still needs live-provider test-mode verification before enabling it.
3. Enter actual products, permitted product photos, opening stock, selling units, prices, and genuinely serviceable pincodes with transport charges/minimums/estimates. Migration creates no production zones; seed zones are development examples. Reconcile counter sales and deliveries daily through the ledger.
4. Finalize business identity, support contact, privacy/retention/backup terms, cancellation/refund rules, and the accountant-approved GST invoice workflow. Public privacy/deletion routes are implemented, but legal and Play Console declarations are not completed for the owner.
5. Build a signed Android app and test on real devices/slow networks before Android distribution. Assess/remediate the Expo advisories; configure and test image storage and Android notifications as needed. iOS push remains a separate integration task.
6. Rehearse one complete production COD order, cancellation, delivery, and cash reconciliation; run a representative concurrent checkout test and train the operator. No production capacity guarantee for 50–100 customers is claimed from local correctness tests. Expand from 10–20 known customers only after real fulfilment is reliable.

Bulk quote conversion, partial refunds, statutory invoices, fractional/multiwarehouse stock, and contractor credit/pricing remain intentionally outside this pilot scope. Customer deletion retains de-identified financial records; historical backups follow the owner's disclosed retention process.
