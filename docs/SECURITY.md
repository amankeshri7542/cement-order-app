# Security review

Reviewed 2 October 2026. This is an implementation review and automated verification, not an independent penetration test.

## Boundaries verified

| Area                | Controls and evidence                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authentication      | Random six-digit development OTP, keyed hash at rest, expiry, one-time consume, five-attempt cap, per-phone resend/hour limits, plus persistent hashed-IP budgets across phone numbers (10 sends/10 minutes, 30 sends/hour, 30 verifications/10 minutes); Twilio Verify adapter for production. Tests verify consumption and brute-force limits.                                                                                                                                                                                                |

Tests attempt cross-customer access.                                                                                                                                                                                                                                                                                                                                                                                                                                               |

| Money               | Integer paise, safe-integer/overflow checks, total recalculation from current DB products and store policy. | Price changes       | Server-created, expiring reviews bind to customer/cart/product versions/store-policy version and pincode-zone identity/version. The order transaction revalidates all of them. HTTP and browser tests change prices between review and placement and require explicit renewed acceptance.                                                                                                                                                                                                                                                                                                                                                           |
| Inventory           | SERIALIZABLE transactions with bounded retries and conditional stock decrements. Concurrent last-stock purchase test produces one order and one rejection. Purchase, walk-in sale, online reservation, cancellation, return, damage, and manual adjustment all create idempotent movement records in the same transaction as the balance update. A database trigger rejects movement updates/deletes. Direct product balance editing is rejected. | Payments            | Gateway orders use saved totals. Callback HMAC is verified and provider details are fetched, but callbacks do not mark an order paid. | Refunds / expiry    | Unpaid ONLINE stock reservations expire. COD demand is never automatically cancelled or released. Unsupported partial or mismatched refunds do not silently change state.                                                                                                                                                                                                                                                                                                  |
| Quotations          | Every item must be priced exactly once. Versioned offers have expiry. Acceptance/rejection is bound to the reviewed revision; accepted quotes are immutable. Customer and store-recorded decisions carry distinct provenance; staff must provide evidence. Revised offers clear prior decision metadata. Staff actions are separately authorized and audited.                                                                                                                                                                                                                                                                                       |
| Output / logging    | React renders user data as text; no untrusted HTML insertion. API errors return stable codes and request IDs without stack traces. Logs omit tokens, OTPs, credentials, request bodies and full gateway payloads. Only payment identifiers, event hashes and business audit details are persisted.                                                                                                                                                                                                                                                                                                                                                  |

## Dependency review

`npm audit --omit=dev --workspace @shiv/api` reports **zero advisories** at the final recorded check. Backend/tooling fixes include current Firebase Admin and Vitest, plus scoped overrides for Prisma configuration dependencies, Swagger YAML and Google client UUID.

The full monorepo audit still reports upstream Expo tooling advisories, principally **node-forge signature parsing** and **xcode’s old UUID dependency**. These affect the development/native build dependency tree; they are not a reason to downgrade the application to an incompatible obsolete Expo SDK. Review and resolve these before enabling Expo code signing or approving a production mobile release. See the implementation report for the final package counts.

## Operational limits requiring action before release

- Test real OTP delivery and provider fraud controls, gateway test payments/webhook delivery/refunds, Android push and R2 uploads using actual accounts.
- V1 runs a single API instance; in-process rate limits/SSE and the notification worker are not distributed. Use an always-on service and explicit proxy trust.
- Configure encrypted PostgreSQL transport, backups, restore testing, monitoring and retention/deletion policy for customer data and audit history.
- Indian GST/tax handling, statutory invoice numbering, store legal details and consumer/refund terms need the owner’s business decisions. The app currently exposes an honest order summary, not a GST invoice.
- Verify device storage, native keyboard/back behavior, real payment app handoffs and accessibility with Android/iOS builds. No signed mobile build has been exercised in this workspace.

## Pilot hardening review (2 October 2026)

- Exact pincode zones are authoritative at review and placement; unknown/inactive zones fail closed. Delivery fees, minimums, free thresholds, and zone versions are checked server-side.
- Uncertain gateway initialization stays locked. Staff reconciliation independently verifies provider order identity, receipt, amount, and currency, then binds it in a Serializable transaction. Concurrent reconciliation cannot overwrite the verified association or create a second provider order.
- Contractor signup is only a PENDING verification request. Audited staff approval is required for the CONTRACTOR role. No preferential pricing or credit is implemented.
- Account deletion revokes sessions/devices, clears profile/address/contact snapshots and free-text notes, and retains de-identified financial/audit data. Open orders/refunds block deletion. Public privacy and verified deletion pages exist; final retention periods, backup policy, legal identity, and Play disclosures remain owner launch prerequisites.
- Cursor payloads are size/type validated and tied to filter/sort fingerprints; they convey no authorization. All customer list queries still scope records to the authenticated owner. Page size is limited to 100.
- Review caught two regressions and tests now guard them: deleted-customer notes remaining in status/audit records, and old decision provenance surviving quote revision. Neither is intentionally deferred.

The full dependency audit still reports **11 affected packages (4 high, 7 moderate)** in the Expo tooling chain. Do not apply the suggested force downgrade to Expo 44. Assess a supported Expo/toolchain remediation before native release. No production provider or signed-device behavior is proven by local tests.

## Rate Studio boundary

Rate Studio endpoints require ADMIN authorization, including original source reads and card downloads. Source images are signature/decoder checked, size bounded and privately stored; object keys are content-addressed and verified on read. External outputs are schema validated and cannot directly update prices. Publication requires reviewed mappings and current product versions. Immutable database evidence, per-staff attempt limits, timeouts and safe usage logs protect the workflow. Live provider policies and handwriting accuracy still require staging verification; see [Rate Studio privacy and operational limits](RATE_STUDIO.md).

### Demand and cost controls

`AuthRateLimit` now also stores HMAC-keyed persistent budgets and expiring resource leases. Serializable transactions enforce customer/IP/store admission budgets and pending-demand caps together with order/quote creation. An idempotent successful retry returns the saved result before budgets or emergency switches are checked. Rejected orders do not reserve stock or consume an owner exception. Caps count pending, unacknowledged, unpaid CONFIRMED COD orders; dispatched/paid/refund work is never released by these controls. Owners must investigate old demand. Acknowledging legitimate work removes it from the pending cap while keeping its stock reserved. Reviewed quote conversion remains available for legitimate wholesale.

| Setting                                                              | Default and meaning                                                                                                          |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `PENDING_COD_CUSTOMER`, `PENDING_COD_STORE`                          | 3 / 25 unacknowledged COD orders                                                                                             |
| `PENDING_COD_CUSTOMER_PAISE`, `PENDING_COD_STORE_PAISE`              | 10000000 / 100000000 paise (₹1 lakh / ₹10 lakh)                                                                              |
| `PENDING_COD_STOCK_PERCENT`                                          | 50% of available plus unacknowledged reserved quantity, at least the product minimum selling quantity                        |
| `PENDING_QUOTES_CUSTOMER`, `PENDING_QUOTES_STORE`                    | 3 / 30 unacknowledged REQUESTED quotes                                                                                       |
| `ORDERS_PER_ACCOUNT_HOUR`, `QUOTES_PER_ACCOUNT_HOUR`                 | 10 each; hashed-IP cap is five times the account cap                                                                         |
| `DEMAND_PER_DAY`                                                     | 500 orders and 500 quotes per store window; valid checkout reviews capped at 60/account/hour, 300/IP/hour and 5000/store/day |
| `OTP_SENDS_PER_DAY`, `OTP_CHECKS_PER_DAY`                            | 200 / 1000 global attempts, in addition to existing phone/IP/attempt limits                                                  |
| `EXTRACTIONS_PER_DAY`                                                | 50 global extraction attempts; existing 20/staff/hour, 5/batch, 2 processing leases remain                                   |
| `DEMAND_PAUSED`, `OTP_PAUSED`, `EXTRACTION_PAUSED`, `UPLOADS_PAUSED` | literal `true`/`false`, default false; restart API to apply                                                                  |

Windows begin with the first counted request, not at midnight. Demand counters count admitted operations; malformed/rejected requests also face the existing process-local request throttle and must face edge limits in staging. An extraction can make multiple provider calls/retries: 50 extraction attempts is **not** a monetary cap. Account/IP/global budget keys never contain raw phone numbers or IPs. Threshold audit events and structured `SECURITY_BUDGET_WARNING` logs occur at 80%; `SECURITY_REQUEST_REJECTED` logs contain request ID/status/time, without bodies or credentials. Owner Finance & settings → Booking limits shows pending work, COD older than two hours, and recent warnings. Configure external alert delivery separately. Threshold logs can repeat on transaction retries or a later rollback; use committed audit records for accounting and deduplicate alerts by scope/window.

Finance & settings also provides a one-use, 30-minute exception for one existing customer's phone, request type, maximum COD amount (up to ₹10 lakh), and required review reason. `DEMAND_OVERRIDE_GRANTED` and `DEMAND_OVERRIDE_USED` preserve actor/provenance. Exceptions bypass pending caps only; they do not bypass request budgets, pause switches, current prices, stock checks, ownership or idempotency. A replacement invalidates the previous unused exception. Do not grant exceptions just to clear an alert.

Provider concurrency: at most four active Twilio calls (10-second fetch timeout, 15-second crash-recovery lease), two public-photo jobs (60-second lease; each decoder stage at most 5 seconds, storage request 30 seconds), and existing two Rate Studio jobs (45-second provider timeout with bounded retries and persisted job leases). Database transactions retain bounded retry/timeouts. API request-body/header timeouts are 30/10 seconds. Expired budgets/leases and old exceptions are cleaned in bounded/dated maintenance. These application controls do not prevent network DDoS or replace provider spending controls.

### Browser and image policy

Next.js dynamically renders with a fresh CSP nonce. Production scripts permit neither unsafe-inline nor unsafe-eval; styles retain unsafe-inline for current UI styling. The exact API origin is allowed for authenticated Rate Studio previews and connections. Public product image origins come from `NEXT_PUBLIC_ASSET_ORIGIN` / `EXPO_PUBLIC_ASSET_ORIGIN`, matching API `R2_PUBLIC_URL`. Set frontend API origins at build time and serving time consistently.

Customer production exports are served by `npm run serve:customer` (loopback behind the staging TLS proxy) with enforced CSP, nosniff, frame denial, no-referrer and HSTS. Its exported script is external; there is no production inline/eval allowance. Fixed Razorpay script/frame origins preserve the existing separately-gated payment integration; payments remain disabled. If using another static host, port these headers and verify actual responses there. Merely exporting Expo files does not install hosting headers.

Expo's HTML handler precedes Metro's middleware hook. `npm run dev:web` therefore uses `scripts/customer-web.mjs`, a loopback response wrapper around Expo on port 8091 (browser port 8081); browser tests use 8092/8082. Development script policies allow required tooling; those exceptions are absent in production. Never expose Metro/Next development servers for staging.

Production rejects non-HTTPS or credential/query-bearing object-store endpoints before connecting. Public photos use authenticated `POST /admin/uploads` with actual raster bytes; direct public presigned PUTs are removed. Only after a successful bounded WebP write is a `ProductAsset` recorded. Unknown external URLs, guessed keys, SVG, MIME mismatch, truncation, oversized bytes and excessive pixels are rejected. Legacy image URLs must be reviewed and re-uploaded before publishing a product edit; audit existing catalogue images before staging. Rate Studio supplier images stay private, credentials server-side, AI output strictly validated, and publication requires human review. Real object-store policies, separate private/public buckets, restricted tokens, no listing, content headers and lifecycle cleanup remain deployment checks.

### Database, backup and incident operation

Use separate staging resources and secrets. Give the release job migration/extension privileges; give API only a non-owner runtime role with schema USAGE and table DML. `scripts/runtime-grants.sql` is an operator-reviewed template. Production startup rejects superuser, role/database creation, BYPASSRLS, role memberships, schema CREATE and public-object ownership. Do not feed migration credentials to the runtime image. The container runs as the existing non-root user; actual image build/CVE scan and pinned image digest remain required.

`npm run test:restore` is restricted to a local `_test` source, restores a custom-format dump into a uniquely named disposable database, compares every table, checks restricted runtime CRUD and denied DDL/migration/ledger writes, then drops only that generated database and role. It never resets development. This rehearsal is not evidence of managed backup encryption, retention, PITR, restore speed at production scale, or off-site availability.

Before staging, assign a backup/incident operator. Proposed family-staging target: encrypted daily backups, 7-day retention, RPO 24 hours, RTO 4 hours; the family must approve and the provider must demonstrate them. For real backup: use PostgreSQL 16 tools, a restricted `PGSERVICE`/0600 `PGPASSFILE` (not credentials in argv), `pg_dump --format=custom --no-owner --no-privileges --file=STAGING.dump`, encrypt immediately to the approved backup destination, and test restoration into a new isolated database with providers disabled. Verify row counts, stock/financial invariants, migration version and a test login. Never overwrite the live database to rehearse.

Incident sequence: technical operator pauses the affected feature or stops public ingress; preserve redacted logs/audit/backup evidence; revoke affected sessions and provider keys; rotate staff passphrases as appropriate; reconcile orders, stock and provider receipts with owners; restore only to a separate database; verify before switching traffic. Never auto-refund, cancel paid/dispatched work or replay provider operations to fix an uncertain outcome. For SMS/OCR cost abuse, use provider-side emergency disable too. Resume only after root-cause and invariant checks. No real messages or payment operations were used to test this sequence.
