# Security review

Reviewed 2 October 2026. This is an implementation review and automated verification, not an independent penetration test.

## Boundaries verified

| Area                | Controls and evidence                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authentication      | Random six-digit development OTP, keyed hash at rest, expiry, one-time consume, five-attempt cap, per-phone resend/hour limits, plus persistent hashed-IP budgets across phone numbers (10 sends/10 minutes, 30 sends/hour, 30 verifications/10 minutes); Twilio Verify adapter for production. Production startup rejects mock OTP. Tests verify consumption and brute-force limits.                                                                                                     |
| Sessions            | 256-bit opaque tokens; only SHA-256 hashes stored in PostgreSQL. Access expiry 30 minutes; rotating refresh token with a fixed 30-day customer session lifetime and eight-hour staff lifetime. Customers and staff can inspect their own session metadata and revoke other sessions/devices. Old access/refresh tokens stop working after rotation. Logout revokes the session and its push devices. Native refresh token stored in SecureStore, browser credentials in HttpOnly cookies. |
| Admin authorization | Database role checked on each request; signup cannot choose ADMIN. An explicit CLI grants owner access and stores a per-user scrypt passphrase hash in a separate credential table. Production staff login requires OTP plus that passphrase. Credential rotation revokes sessions; assurance is rechecked on every request. Credentialless staff access exists only for development/test fixtures. Customer access to admin routes is rejected in HTTP and browser tests.                |
| CSRF / CORS         | Browser writes require an exact allowed Origin. Cookies use SameSite=Lax and Secure in production. Deployment requires sibling subdomains to avoid third-party cookies. Configure trusted proxy hops accurately before relying on IP throttling behind a proxy.                                                                                                                                                                                                                           |
| IDOR                | Address, cart, review, order, order summary and quote queries are constrained to the authenticated owner. Only guarded staff endpoints can view other customers. Tests attempt cross-customer access.                                                                                                                                                                                                                                                                                     |
| Validation          | Shared strict Zod schemas reject unknown properties, including injected prices, roles and totals. Quantities, text lengths, identifiers and amounts are bounded. Prisma parameterizes normal queries. Brand discovery uses parameterized bounded SQL; the isolated test reset uses a hard-coded raw TRUNCATE statement.                                                                                                                                                                   |
| Money               | Integer paise, safe-integer/overflow checks, total recalculation from current DB products and store policy. Database CHECK constraints reject negative stock, invalid quantities and inconsistent saved totals.                                                                                                                                                                                                                                                                           |
| Price changes       | Server-created, expiring reviews bind to customer/cart/product versions/store-policy version and pincode-zone identity/version. The order transaction revalidates all of them. HTTP and browser tests change prices between review and placement and require explicit renewed acceptance.                                                                                                                                                                                                 |
| Inventory           | SERIALIZABLE transactions with bounded retries and conditional stock decrements. Concurrent last-stock purchase test produces one order and one rejection. Purchase, walk-in sale, online reservation, cancellation, return, damage, and manual adjustment all create idempotent movement records in the same transaction as the balance update. A database trigger rejects movement updates/deletes. Direct product balance editing is rejected. Cancellation restores stock once.       |
| Payments            | Gateway orders use saved totals. Callback HMAC is verified and provider details are fetched, but callbacks do not mark an order paid. Raw webhook HMAC, provider-order binding, amount/currency/status matching and unique event IDs gate state changes. Identical events are idempotent; altered content under an existing event ID is rejected.                                                                                                                                         |
| Refunds / expiry    | Unpaid stock reservations expire. A capture after cancellation creates REFUND_PENDING without reserving stock again. Full processed-refund events update once; cash refunds require staff acknowledgement. Unsupported partial or mismatched refunds do not silently change state.                                                                                                                                                                                                        |
| Quotations          | Every item must be priced exactly once. Versioned offers have expiry. Acceptance/rejection is bound to the reviewed revision; accepted quotes are immutable. Customer and store-recorded decisions carry distinct provenance; staff must provide evidence. Revised offers clear prior decision metadata. Staff actions are separately authorized and audited.                                                                                                                             |
| Output / logging    | React renders user data as text; no untrusted HTML insertion. API errors return stable codes and request IDs without stack traces. Logs omit tokens, OTPs, credentials, request bodies and full gateway payloads. Only payment identifiers, event hashes and business audit details are persisted.                                                                                                                                                                                        |
| Uploads             | Staff-only short-lived object upload URLs, random keys, limited raster MIME types and declared size; separate asset host required. Actual R2 enforcement remains to be verified with configured storage.                                                                                                                                                                                                                                                                                  |

## Dependency review

`npm audit --omit=dev --workspace @shiv/api` reports **zero advisories** at the final recorded check. Backend/tooling fixes include current Firebase Admin and Vitest, plus scoped overrides for Prisma configuration dependencies, Swagger YAML and Google client UUID.

The full monorepo audit still reports upstream Expo tooling advisories, principally **node-forge signature parsing** and **xcode’s old UUID dependency**. These affect the development/native build dependency tree; they are not a reason to downgrade the application to an incompatible obsolete Expo SDK. Review and resolve these before enabling Expo code signing or approving a production mobile release. See the implementation report for the final package counts.

## Operational limits requiring action before release

- Test real OTP delivery and provider fraud controls, gateway test payments/webhook delivery/refunds, Android push and R2 uploads using actual accounts.
- V1 runs a single API instance; in-process rate limits/SSE and the notification worker are not distributed. Use an always-on service and explicit proxy trust.
- Configure encrypted PostgreSQL transport, backups, restore testing, monitoring and retention/deletion policy for customer data and audit history.
- Indian GST/tax handling, statutory invoice numbering, store legal details and consumer/refund terms need the owner’s business decisions. The app currently exposes an honest order summary, not a GST invoice.
- Verify device storage, native keyboard/back behavior, real payment app handoffs and accessibility with Android/iOS builds. No signed mobile build has been exercised in this workspace.

## Pilot hardening review (2 October 2026)

- Exact pincode zones are authoritative at review and placement; unknown/inactive zones fail closed. Delivery fees, minimums, free thresholds, and zone versions are checked server-side.
- Uncertain gateway initialization stays locked. Staff reconciliation independently verifies provider order identity, receipt, amount, and currency, then binds it in a Serializable transaction. Concurrent reconciliation cannot overwrite the verified association or create a second provider order.
- Contractor signup is only a PENDING verification request. Audited staff approval is required for the CONTRACTOR role. No preferential pricing or credit is implemented.
- Account deletion revokes sessions/devices, clears profile/address/contact snapshots and free-text notes, and retains de-identified financial/audit data. Open orders/refunds block deletion. Public privacy and verified deletion pages exist; final retention periods, backup policy, legal identity, and Play disclosures remain owner launch prerequisites.
- Cursor payloads are size/type validated and tied to filter/sort fingerprints; they convey no authorization. All customer list queries still scope records to the authenticated owner. Page size is limited to 100.
- Review caught two regressions and tests now guard them: deleted-customer notes remaining in status/audit records, and old decision provenance surviving quote revision. Neither is intentionally deferred.

The full dependency audit still reports **11 affected packages (4 high, 7 moderate)** in the Expo tooling chain. Do not apply the suggested force downgrade to Expo 44. Assess a supported Expo/toolchain remediation before native release. No production provider or signed-device behavior is proven by local tests.
